How Do Small Coding Agents Use Code Graphs and Embeddings? A depth-stratified study of issue localization on SWE-bench Verified, with tool ablations, a 0.6B–32B scale curve, downstream repair, and linear probes of the repository graph
Saurav Bellam
Abstract
Coding agents are given embedding search and code-graph tools on the premise that a repository’s structure is something the model lacks and the tool supplies. We test that premise on SWE-bench Verified with small open-weight models. First, we label all 500 tasks with a deterministic hop depth: the shortest code-graph path from code the issue mentions to code the gold patch changes (186/128/78/76 tasks at hop 0/1/2/3+). With repository, tool-set and patch-size controls, each extra hop multiplies the odds of correct function-level localization by 0.47–0.55 for Qwen3–4B, Qwen3–8B, Gemma 4 E4B and Qwen3–32B, and by 0.50–0.67 at each of six Qwen3 sizes from 0.6B to 32B. Second, we ablate a localization agent’s tool set (grep only; +embedding search; +graph tools; all) on a depth-balanced 160-task split and on all 500 tasks for ten models (79k episodes). Structured tools double grep-only accuracy for Qwen3–8B and Gemma 4 E4B; their gain peaks at 17–21 points at 1.7–4B and falls to 4–5 points at 32B (odds ratio 0.77–0.82 per doubling of parameters). From 8B up, about half of that gain is the form of the submission rather than finding the target; the fall from 14B to 32B is a fall in tool uptake at equal grep-only accuracy; and the same 4B size gains or does not gain from a tool depending on the checkpoint. Traces show the graph tools’ gain is name lookup at hop 0 and one expansion at hop 1: agents chain expansions in 12–14% of episodes and never flatten the depth gradient. A fixed repair model resolves 6–13 of 160 tasks from these localizations (oracle 26). Third, linear probes find direct call edges decodable under a within-anchor, degree-stratified protocol (AUC 0.74), but below a lexical baseline (0.99), with two-hop edges at 0.57. Small agents carry a one-hop, largely lexical picture of their repository, in weights and in use. We release the labels, scripts, logs and traces.

Introduction
Resolving a GitHub issue in a large repository starts with finding the code that has to change. Agentic systems for this
localization
step increasingly ship with structured tools: dense retrievers over function bodies, and query interfaces over a static code graph whose nodes are files, classes and functions and whose edges record containment, imports, calls and inheritance
(Chen et al., 2025a; Yu et al., 2025; Jiang et al., 2025; Yang et al., 2025)
. The working assumption behind these tools is simple. An issue names some code; the fix lives some distance away along the dependency structure; a plain text search cannot bridge that distance, so the agent needs either a semantic index (to jump directly to code that means the right thing) or a graph (to walk to it). LocAgent
(Chen et al., 2025a)
made the assumption measurable by scoring SWE-bench tasks by the hop distance between the functions an issue mentions and the functions the patch edits, and reported that graph-guided agents degrade least as that distance grows. CodeAnchor
(Lin et al., 2026)
observed that SWE-bench Lite and Verified contain mostly one- and two-hop faults, and argued that evaluating structure-aware agents properly “requires a benchmark that sorts tasks by structural depth”.
This paper takes that argument seriously and asks three questions that the existing literature leaves open, using small open-weight models where the behaviour is cheap to measure many times over and where tool support plausibly matters most.
Part 1. Is structural depth a usable difficulty axis?
We compute, for every SWE-bench Verified task, a deterministic hop depth on a LocAgent-style graph built at the task’s base commit (Section 3). Unlike LocAgent’s measurement, which extracted mentions with GPT-4o, ours uses only regular expressions and the Python
ast
module, so it can be re-run, audited and varied. We ask how the 500 tasks are distributed over depth, whether depth predicts whether an agent localizes the fix after controlling for repository, tool set, number of gold functions and patch size (DepthGEE), how sensitive the label is to the two measurement choices that matter—how calls are resolved and how mentions are extracted (LabelVar)—and we release the labelled split.
Part 2. What do
grep
, embedding search and graph tools each contribute?
On a 160-task subset balanced over depth we run a localization-only agent whose arms differ
only
in their tool set:
G
(grep, read_file, list_dir),
E
(G + embedding search over function and class texts),
T
(G + a name lookup and a one- or two-hop neighbourhood query over the graph) and
ET
(all tools) (Section 4). We measure accuracy by depth, run-to-run variance under sampling, which tool first exposes the gold code and whether exposure converts into a correct submission, sensitivity to retrieval quality, the effect of forcing the structured tool to be used, the effect of a larger step and context budget, and—because localization is only useful if it leads to a fix—how many issues one fixed repair model resolves when given each arm’s localizations (Section 5). We then rerun the four arms on all 500 tasks across a model-size curve: six Qwen3 sizes from 0.6B to 32B with five decodings each, an FP8 precision control, and three Gemma 4 sizes (Section 5.4).
Part 3. Does the model represent the repository’s graph internally?
The “Thousand-Graph Hypothesis”
(Ding, 2026)
proposes that an entity-only index suffices because self-attention materialises whatever relation a task needs; a recent probe shows that the
runtime tool-call
dependency structure of an agent is linearly decodable from Qwen3-32B residual streams
(Sun & Kazakov, 2026)
. Neither probes the repository’s own call and inheritance graph. We do, with linear probes on definition-level activations, first in static file contexts (GlobalProbe, AnchorProbe) and then inside real agent conversations (ConvProbe). The design is driven by a negative result we obtained early on: a global pair probe reaches AUC 0.75–0.80 for call edges, but so does a probe that sees only one of the two definitions, and so does the in-file in-degree of the callee. Linked and unlinked pairs differ in properties of a
single
node. We therefore introduce a within-anchor ranking protocol with an in-degree-binned stratification that a node-level shortcut cannot pass, with bootstrap intervals over anchors and a lexical name-match baseline (Section 6).
Findings.
The answers are consistent across two model families and six sizes, and point in one direction.
•
Hop depth is a strong, controlled predictor of failure. Each extra hop multiplies the odds of correct function-level localization by 0.47 (Qwen3-4B, three runs), 0.47 (Qwen3-8B), 0.54 (Gemma 4 E4B, three runs) and 0.55 (Qwen3-32B, all 500 tasks), with all
p\leq 10^{-3}
; across the scale curve the per-hop odds ratio is 0.50–0.67 at every size and barely changes with size. The label barely moves under alternative call resolution (\kappa=0.96 – 0.98). It is, however, sensitive to mention extraction: a strict extractor that counts only back-ticked code and traceback frames leaves 311 of 500 tasks without a mention.
•
For Qwen3-8B and Gemma 4 E4B,
grep
alone is a weak baseline (12.8% and 9.6% function Acc@10) that any structured tool roughly doubles. For Qwen3-4B the embedding tool adds nothing (-1.1 points) and the graph tools add
+8.1
points ([3.0,\,13.5]). In every model, the graph-tool advantage is largest at hop 0, where the issue names the target and
find_entity
resolves the name directly, and at hop 1, where one
graph_neighbors
expansion reaches it; at hop 2+ the gain shrinks or vanishes, and in a GEE interaction model the depth slope of
T
is never significantly flatter than that of
G
(it is steeper in the Qwen models) while
E
has the flattest slope. Small graph-tool agents do not walk the graph; they look names up and expand once. Over the scale curve, the structured tools’ gain over
grep
rises from 7–9 points at 0.6B to 17–21 at 1.7–4B and falls to 4–5 at 32B (odds ratio 0.77–0.82 per doubling of parameters); from 8B up about half of that gain is the
form
of the submission (exact ids) rather than discovery; the fall from 14B to 32B happens at equal
grep
-only accuracy and is a fall in tool uptake (find_entity called in 96% of episodes at 14B, 45% at 32B), not an FP8 artifact; and the same 4B size gains
+17.6
points from embedding search under one checkpoint and nothing under another.
•
Grep-only Qwen3-8B collapses into search loops (10 grep calls per episode, 40% of episodes hit the step cap, 41% never submit); a 50-step, 40k-token budget does not rescue it. Graph tools also change the
form
of what the agent submits: 85% of its top-5 function strings are exact entity ids, against 47% with
grep
only, which matters downstream.
•
Downstream, the localizations of
G
/
E
/
T
/
ET
lead a fixed Qwen3-8B repair prompt to 6/13/12/13 resolved tasks of 160 (oracle locations: 26). Resolution is almost entirely conditional on correct localization (24–27% versus 1–2%).
•
Inside the model, direct call edges are linearly decodable within anchor and in-degree bin (AUC 0.74 and 0.68 on the two held-out folds for Qwen3-4B; 0.73 and 0.66 for Qwen3-8B) and remain so inside agent conversations (0.61–0.66) including for edges no tool printed (0.59–0.60); but a one-line lexical baseline reaches 0.99, two-hop edges with the lexical cue removed reach only 0.57, and inheritance is not decodable beyond one-sided information. What is in the weights is a shallow, mostly lexical picture of direct dependencies.
Contributions.
(i) A deterministic, released hop-depth labelling of SWE-bench Verified with a validated difficulty analysis and a robustness study of the label itself (Section 3). (ii) A controlled, depth-stratified tool ablation with trace-level mechanism analysis, variance, forced-use, budget, retrieval-quality and downstream-repair experiments, and a full-benchmark scale curve over ten models (six Qwen3 sizes from 0.6B to 32B with five decodings each, an FP8 control and three Gemma 4 sizes; 79k episodes) with a canonical rescoring that separates discovery from the form of the submission (Section 5). (iii) A within-anchor, degree-stratified probing protocol for relational structure, with the negative control that motivates it, applied both to static code and to activations taken inside agent conversations (Section 6). (iv) A synthesis: with small models, the benefit of “structure” tools is exact-name resolution plus one hop, which is also the extent of the structure the models appear to carry internally, and which shrinks with scale as the models stop calling the tools; deeper tasks are failed by every arm at every size (Section 7).
All numbers in this paper are computed from the episode logs, traces, probe scores and harness reports described in the reproducibility statement; the depth labels, source code, raw result files and analysis scripts are public (see the reproducibility statement).

Related work
Graph tools versus one-shot retrieval as depth grows.
LocAgent
(Chen et al., 2025a)
builds a heterogeneous code graph (file, class, function nodes; contain, import, invoke, inherit edges) and gives an agent tools to search entities, traverse the graph and retrieve code. Its difficulty analysis (App. C.1.2) measures the shortest hop between the functions an issue names and the patched functions, finds accuracy falling with depth for every method, and reports that embedding retrievers (E5, CodeRankEmbed) and Agentless
(Xia et al., 2024)
fall furthest at hop 3+ while graph-tool agents degrade least. SWE-Explore
(Zhang et al., 2026b)
finds that sparse retrievers and a lightweight static-embedding retriever “remain close to Random on most metrics” whereas all agentic explorers score much higher. A family of graph-guided localizers follows the same design: OrcaLoca
(Yu et al., 2025)
, iterative code-graph search
(Jiang et al., 2025)
, repository-aware knowledge graphs
(Yang et al., 2025)
, conceptual-knowledge extraction
(Wang et al., 2025c)
, unified knowledge graphs for multilingual issue resolution
(Chen et al., 2025b)
, tool-integrated RL for repository search
(Ma et al., 2025)
, repository memory
(Wang et al., 2025a)
, multi-language localization
(Vats et al., 2026)
, location inference for task-level understanding
(He et al., 2026)
and exploration structure for multi-file changes
(Fattha et al., 2026)
. Our study differs in three ways: the models are small (4–8B), the tool sets are ablated one at a time on the same tasks with the same harness, and the depth axis is used as a stratification variable with controls rather than as a post-hoc breakdown. Our result on depth differs from LocAgent’s at hop 3+: with small models the graph arm’s depth slope is no flatter than
grep
’s.
Embeddings that know about structure.
SpIDER
(Chaudhari et al., 2025)
adds graph-neighbourhood information to dense retrieval for issue localization; Meta-RAG
(Tawosi et al., 2025)
retrieves over LLM summaries of code; ProjAgent
(Chen et al., 2026)
retrieves by procedural similarity for repository-level generation; CORE-Bench
(Zhang et al., 2026a)
and Agent Retrieval Bench
(Qin & Xie, 2026)
evaluate repository retrieval for agents;
Oskooei et al. (2026)
compare a vector index with grep-style agentic search for repository QA. Our embedding arm uses a standard instruction-tuned embedder (Qwen3-Embedding-0.6B) over function and class texts without structural augmentation, which is the configuration whose contribution we want to isolate; the
WeakEmb
experiment (Section 5.6) swaps in a weak static embedder to measure how much of the arm’s effect is retrieval quality.
How structure is shown to the agent.
RepoNav
(Chai et al., 2026)
reorganises flat snippet retrieval into a file-centred scaffold and finds that the
organisation
of structure helps beyond its volume (File-Only 32.6% \to Inline 47.0% \to Tree 52.1% function Acc@5). CodeAnchor
(Lin et al., 2026)
and LARGER
(Hu et al., 2026)
inject structure into
grep
results instead of adding tools. Rendering the repository as an image also helps
(Ma et al., 2026)
; incremental code indexes can silently serve wrong graphs
(Yu et al., 2026)
; context files did not measurably move correctness in a two-agent ablation
(Khatri, 2026)
; ontology-grounded project memory exposes design rationale as a knowledge graph
(Adam, 2026)
. DeepRepoQA
(Peng et al., 2026)
and agentic code reasoning with semi-formal certificates
(Ugare & Chandra, 2026)
target understanding rather than localization. Our
T
arm presents structure in the plainest way (one line per edge, truncated at 50 lines), and our trace analysis (Section 5.5) shows which of those lines the agent actually acts on.
Do models represent the graph internally?
The Thousand-Graph Hypothesis
(Ding, 2026)
proposes that an entity-only index suffices because self-attention materialises task-specific relations; its two-layer index reaches 95.6% on SWE-bench Verified with DeepSeek-V4-Flash, but the author notes this “does not directly verify the latent graph realized inside the model”.
Sun & Kazakov (2026)
decode an agent’s
runtime tool-call
dependency graph from Qwen3-32B residual streams above random-label and positional controls, and are careful that their “claims concern representation, not behavioural control”. Neither probes the repository’s call or import graph. Our probes do, and the protocol we arrive at—within-anchor ranking with degree stratification, a permuted-label control and a lexical baseline—is a direct response to the node-level confounds we document in
Section
6.2
. The general concern that pair probes can be solved by single-item features is the relational analogue of the selectivity argument of
Hewitt & Liang (2019)
.
Controlled difficulty.
CABRA
(Balepur et al., 2026)
builds synthetic tasks as call-graph transformations and finds that agents stay near-perfect as task size grows because they offload to tools such as
grep
, and that tool-call counts predict SWE-bench Verified accuracy better than lines edited. CodeAnchor
(Lin et al., 2026)
observes that SWE-bench Lite and Verified mostly contain one- and two-hop faults. Our depth labels quantify that observation on Verified (67% of tasks with a mention are at hop 0 or 1) and supply the sorted benchmark CodeAnchor asks for. Graph retrieval for repository-level code
generation
is adjacent but not our topic
(Li et al., 2025; Wang et al., 2025b; Liu et al., 2026; Le-Anh et al., 2026; Li et al., 2026; Bai et al., 2026)
.

Part 1: Hop depth as a difficulty axis
3.1
Code graph
For each SWE-bench Verified
(Jimenez et al., 2024; OpenAI, 2024)
instance
i
we check out the repository at its
base_commit
and parse every
.py
file with the Python
ast
module (files that fail to parse contribute a file node only). The result is an undirected, typed multigraph
\displaystyle\mathcal{G}_{i}
\displaystyle=(V_{i},E_{i}),\qquad V_{i}=V^{\mathrm{file}}\cup V^{\mathrm{class}}\cup V^{\mathrm{func}},
(1)
\displaystyle E_{i}
\displaystyle\subseteq\tbinom{V_{i}}{2}×\{\textsc{contain},\textsc{import},\textsc{invoke},\textsc{inherit}\},
following LocAgent
(Chen et al., 2025a)
. A function or class node is identified by its path and qualified name,
path/to/mod.py:Class.method
; its span
[s_{v},e_{v}]
is the line range of the definition including decorators. Edges are produced as follows.
•
contain
: file
\to
top-level definition, class
\to
member, for definitions nested in
if
/
try
/
with
/
for
/
while
blocks as well.
•
import
: file
\to
file for every
import m
or
from m import x
, resolving relative imports from the importing module’s package; a dotted module is shortened to its longest prefix that is a file in the snapshot, and self-imports are dropped.
•
invoke
: function
\to
definition for every
ast.Call
whose callee is a bare name or an attribute. Resolution is by name with a fixed preference order: a
self.x()
/
cls.x()
call prefers methods of the enclosing class; otherwise definitions in the same file; otherwise definitions in the module that
from
-imported the name; otherwise every definition of that name in the repository, provided there are at most
K_{\mathrm{res}}=5
of them (ambiguous names are dropped).
•
inherit
: class
\to
class for each base expressed as a name or attribute, resolved the same way and kept only if the target is a class.
Snapshots are large: a mean of 26,242 nodes and 232,915 edges (median 34,919 and 183,269; maximum 45,677 and 1,024,494). Name-based resolution is deliberately cheap; its consequences are measured in
Section
3.5
.
3.2
Targets, mentions and depth
Definition 1
(Targets)
.
Let
P_{i}
be the gold patch. For each removed line at old-side line number
\ell
in file
f
, and for each added line at the old-side position before it, the target is the innermost definition
v
with
f_{v}=f
and
s_{v}\leq\ell\leq e_{v}
(the file node if the line is at module level).
T_{i}\subseteq V_{i}
is the set of all such targets.
Definition 2
(Mentions)
.
Let
D_{i}
be the issue text. A mention is a token produced by one of six regular-expression patterns: back-ticked spans, identifiers immediately followed by
(
, traceback frames
File "...py", line n, in f
, dotted names,
snake_case
names and
CamelCase
names; every token is further split into identifier-like pieces. A token ending in
.py
maps to every file whose path equals or ends with it; any other token of length
\geq 3
maps to every definition with that short name, unless more than
K_{\mathrm{men}}=20
definitions share it, in which case it is treated as too generic and discarded.
M_{i}=\{m_{1},\dots,m_{k}\}
is the set of mentions, each a set of nodes
m_{j}\subseteq V_{i}
.
Definition 3
(Hop depth)
.
Let
d_{\mathcal{G}}(u,v)
be the undirected shortest-path length in
\mathcal{G}_{i}
over a chosen edge-type subset. The depth of a task is
\mathrm{hop}_{i}=\min_{m_{j}\in M_{i}}\ \min_{u\in m_{j},\;v\in T_{i}}d_{\mathcal{G}_{i}}(u,v),
(2)
computed by a breadth-first search from
T_{i}
. The bucket is
\mathrm{hop}0/\mathrm{hop}1/\mathrm{hop}2/\mathrm{hop}3{+}
for
\mathrm{hop}_{i}=0,1,2,\geq 3
;
no_mention
if
M_{i}=\varnothing
or
T_{i}=\varnothing
;
unreachable
if no mention is connected to any target. For comparison we also compute LocAgent’s
\delta_{i}=\frac{1}{|M_{i}|}\sum_{j}\frac{1}{1+d_{j}}
with
d_{j}
the per-mention minimum distance, and the mean per-mention distance.
Hop 0 means the issue names a definition the patch changes (every hop-0 task has at least one mentioned target, and no task in a deeper bucket does). Hop 1 means the nearest mentioned definition is one containment, import, call or inheritance edge away: a method of a mentioned class, a function in a mentioned file, a callee of a mentioned function. Depth is computed from the issue text and the gold patch, so it must never be shown to a system under evaluation; it is a property of the task, not of any agent’s path.

Does depth predict localization failure? (DepthGEE)
We fit a population-averaged logistic model on the episodes of the agent experiments of
Section 5 . For episode
e

i

\logit\Pr(y_{e}=1)=\beta_{0}+\beta_{\mathrm{hop}}\,\mathrm{hop}_{i}^{(3)}+\bm{\beta}_{\mathrm{arm}}^{\top}\mathbf{1}[a_{e}]+\bm{\beta}_{\mathrm{repo}}^{\top}\mathbf{1}[r_{i}]+\beta_{g}\,n^{\mathrm{gold}}_{i}+\beta_{p}\log(1+L_{i}),
(3)
where
\mathrm{hop}_{i}^{(3)}=\min(\mathrm{hop}_{i},3)
,
\mathbf{1}[a_{e}]

G

3.5
Sensitivity of the label to measurement choices (LabelVar)
The two choices most likely to move a label are how a call is resolved and what counts as a mention. We recompute every label under three variants and refit
Eq. 3 for each (Table 1 , lower rows of each block):
•
strict_resolve
:
K_{\mathrm{res}}=1
; a call or base resolves by repository-wide name only if the name is unique (same-file and same-class resolution still apply).
•
loose_resolve
:
K_{\mathrm{res}}=20
.
•
strict_mentions
: only back-ticked spans and traceback frames count as mentions, and
K_{\mathrm{men}}=5
.
Call resolution barely matters.
Strict resolution keeps the bucket of 97.4% of the 500 tasks (Cohen’s \kappa=0.965 ; over the 468 bucketed tasks, 97.2%, \kappa=0.961) and moves 34 tasks deeper and none shallower, as it must since it only removes edges; loose resolution keeps 98.6% (\kappa=0.981) and moves 11 tasks shallower. The odds ratios change by at most 0.02 in any model.
Mention extraction matters.
The strict extractor leaves 311 tasks without any mention: most issues describe their problem with prose identifiers (“the Model.save method”, “ QuerySet.values_list ”) rather than back-ticks or tracebacks. Where it keeps a mention, it agrees with the default bucket on 65.2% of tasks (\kappa=0.527) and is never shallower (71 tasks move deeper, because a dropped mention can only lengthen the minimum path). On the 51 evaluated tasks that keep a mention, the controlled odds ratios are 0.55, 0.42 and 0.68 (the last, for Gemma, not significant at n=612 episodes), and 0.82 for Qwen3-32B on the 185 tasks that keep a mention (p=0.12). The default extractor is therefore the one we release and use throughout, and the labels should be read as
optimistic
: an ambiguous name counts its closest definition and dynamic dispatch is invisible, so the true distance is at least the labelled one.

4.2
Tools and arms
Every arm has the three text tools; the structured arms add one or two more. Tool outputs are lists of lines; each line carries the set of graph nodes it exhibits, which is what makes the trace analysis of
Section
5.5
exact.
•
grep(pattern, path_prefix)
: regular-expression search over all
.py
files, up to 40

•

•

•

(arms E, ET): the ten function or class nodes whose text is closest to the query under Qwen3-Embedding-0.6B
(Zhang et al., 2025)
(last-token pooling, L2-normalised, index text = node id plus the first 40 lines of the definition; query prefixed with the retrieval instruction “Given a description of a software issue, retrieve the code that is relevant”). Each hit is one line,
id signature

•

(arms T, ET): up to 20 nodes whose qualified name equals, ends with

(arms T, ET): breadth-first expansion of the graph of

contains / calls / imports / inherits

4.3
Harness
Models
(Qwen Team, 2025)
are served with vLLM
(Kwon et al., 2023)
through the OpenAI chat-completions interface with native tool calling (hermes parser for Qwen, gemma4 parser for Gemma). Unless stated, decoding is greedy (temperature 0), the step cap is 30 tool calls, and the context window is 32k tokens. Qwen3-8B and Gemma are run with thinking disabled. Two harness rules were found necessary in a pilot and are used in every reported run:
1.
Forced tool call after a bare turn.
If a turn contains no tool call, the harness replies “Use a tool, or call submit with your ranked locations” and sets
tool_choice=required
for the next turn. Without this, greedy decoding frequently repeats the same tool-less message until the step cap; the first full run without the rule (Abl-4B-prefix) is reported in
Table 14 for completeness and is otherwise not used.
2.
Observation budget.
Tool output is truncated at 4,000 characters. A node counts as
revealed
only if it is on a line the model actually received; truncated lines reveal nothing.
Every step is logged with the tool, its arguments, the output as shown, the revealed nodes, the revealed
gold
nodes, token counts and wall-clock time, and the complete message list is saved as a trace. Invalid JSON arguments are replaced by an error observation; an exception from the server (context overflow, timeout) ends the episode. Options used by individual experiments:
--temperature
/
--seed
(Seeds),
--force-first
(ForceTool),
--max-steps
(Budget),
--embedder potion
(WeakEmb).
4.4

Let
S=(s_{1},\dots,s_{n})
be the submitted list,

(4)

\displaystyle=\frac{1}{|G^{\mathrm{f}}|}\sum_{g\in G^{\mathrm{f}}}\mathbf{1}\big[\exists s\in S^{\mathrm{f}}_{1:10}:\mathrm{match}(s,g)\big],
(5)

\displaystyle=\mathbf{1}\big[F\subseteq\mathrm{files}(S)_{1:5}\big],\qquad\text{gold revealed}=\mathbf{1}\big[\exists\,\text{step }t:\ R_{t}\cap G^{\mathrm{f}}\neq\varnothing\big],

Part 3: Does the model represent the repository graph?
The tool ablation says what an agent can extract from structure that is handed to it. We now ask whether the structure is already in the model’s activations, which is what the Thousand-Graph Hypothesis
(Ding, 2026)
asserts, and the kind of question tool-call-graph probing
(Sun & Kazakov, 2026)
answers for a different graph. We probe for three relations between definitions
a
and
b
that both appear in the context:
call
(a calls b directly),
call2
(a reaches b in exactly two call hops and b ’s short name does not occur in a ’s source, so that the lexical cue is removed) and
inherit
(a ’s class inherits from b). Negatives are pairs with no call or inheritance path of length
\leq 2
in either direction; pairs where one definition contains the other are excluded.
6.1
Representations
A context is tokenised and run through the model in a single causal forward pass. Each definition
v
in the context is represented by the residual-stream vector at its
last
token,
\mathbf{h}^{(\ell)}_{v}\in\mathbb{R}^{d}
at layer
\ell
: in a causal model the name token precedes the body, so only the end of the span has read what the definition calls. For a pair
(a,b)
the probe sees
\mathbf{x}_{ab}=\big[\mathbf{h}_{a};\ \mathbf{h}_{b};\ \mathbf{h}_{a}\odot\mathbf{h}_{b}\big]\in\mathbb{R}^{3d},
(7)
and the one-sided controls see
\mathbf{h}_{a}
or
\mathbf{h}_{b}
alone; the interaction-only probe sees
\mathbf{h}_{a}\odot\mathbf{h}_{b}
. Features are standardised with training-set statistics, and a linear logistic probe
\sigma(\mathbf{w}^{\top}\mathbf{x}+c)
is trained by Adam (learning rate 10^{-2} , weight decay 10^{-2} , 300 full-batch steps) on the class-weighted cross-entropy with positive weight
n_{-}/n_{+}
. We probe every fourth layer plus the last (Qwen3-4B and Qwen3-8B both have 36 layers; layer 0 is the token embedding). Folds are repository-held-out: train on the eleven non-Django repositories and test on Django, and the reverse.
6.2
A global pair probe, and why it is not enough (GlobalProbe)
Contexts.
For each of the 468 bucketed tasks we take the first gold-patched file at the base commit (one context per distinct file; 468 contexts, mean 4,668 tokens, truncated at 6,000), with a mean of 34.2 definitions each. Labels come from the whole-repository graph of
Section
3.1
, not just the file. This yields 13,255
call
, 6,405
call2

Result.
The pair probe decodes

call2
reaches 0.70/0.67 and
inherit
0.77/0.80 at later layers. Taken alone these numbers would support a strong reading. The controls do not. A probe that sees only
\mathbf{h}_{a}
reaches 0.71/0.66 on

and

the pair probe on

(0.70/0.69 vs 0.70/0.67) and on

\mathbf{h}_{b}

.
6.3
Within-anchor ranking with degree stratification (AnchorProbe)
To remove node-level shortcuts we score each pair only against other pairs sharing the same anchor. For every anchor
a
that has at least one positive partner, the candidate set is its positives and up to 15 of its negatives from the same context. Let
\mathcal{A}
be the set of groups, each with positives
P_{g}
and negatives
N_{g}
, and let
s(\cdot)
be a score. The metric is the pooled within-group AUC,
\AUC_{\mathrm{grp}}(s)=\frac{\sum_{g\in\mathcal{A}}\sum_{p\in P_{g}}\sum_{n\in N_{g}}\big(\mathbf{1}[s(p)>s(n)]+\tfrac{1}{2}\mathbf{1}[s(p)=s(n)]\big)}{\sum_{g\in\mathcal{A}}|P_{g}|\,|N_{g}|},
(8)
the probability that a random positive outranks a random negative
of the same anchor
. Any feature of
a
alone is constant within a group and cannot help. Under the
strict
grouping, the group is the anchor crossed with the in-degree bin of
b
(bins 0, 1, 2, 3 – 4, 5{+}), so that the popularity of the candidate is held fixed as well; the in-degree baseline then scores 0.50–0.53 by construction. Controls are: the
\mathbf{h}_{b}
-only probe (any remaining node-level signal about b), the interaction-only probe, a pair probe trained on labels permuted
within
each training group, the in-degree baseline, token distance, same-class membership, and the lexical baseline
\mathbf{1}[\text{name}(b)\in\text{text}(a)]
. Per-pair test scores are saved at layers 24 and 36, and 95% intervals are obtained by bootstrapping anchors (2,000 resamples; the numerator and denominator of Eq. 8 are resampled jointly).

7
Discussion
One picture from three parts.
The three parts of the study were designed independently but say the same thing. The hardest third of SWE-bench Verified—hop 2 and hop 3+, 154 tasks—is hard for every arm of every model at every size from 0.6B to 32B, and the tools that are supposed to address exactly this difficulty do not. The graph tools’ contribution is concentrated where the issue names the target (hop 0, where find_entity is a direct lookup) or its immediate neighbour (hop 1, where one graph_neighbors expansion suffices); past that, agents rarely chain expansions (12–14% of episodes) and the arm’s depth slope is at least as steep as
grep
’s. The embedding tool’s contribution is flatter in depth because semantic similarity does not care about graph distance, but it is small in absolute terms (13–28% of first reveals) and depends on retrieval quality. Inside the model, the only relation that is linearly readable beyond node-level confounds is the direct call edge, and even that is a weaker signal than a substring test on the caller’s source. Two-hop structure is essentially absent from the activations, is rarely assembled from the tools, and is where the tasks are failed. Small coding agents operate with a one-hop picture of the repository, in weights and in use. The scale curve adds a fourth strand: what the tools add is largest for the models that cannot
grep
competently (1.7–4B), shrinks by about a fifth of the odds advantage per doubling, is half submission form from 8B up, and disappears at 32B because the model stops calling the tools, with neighbourhood expansion abandoned before name lookup. The structure that is extracted is the one-hop part, and it is extracted less as the model grows.
On the contrast with LocAgent.
LocAgent
(Chen et al., 2025a)
reports that graph-guided agents degrade least with depth. Our graph arm degrades at least as steeply as
grep
alone. The difference is not the graph (ours follows LocAgent’s construction) and is unlikely to be the measurement (our hop label is deterministic and robust to resolution). The plausible differences are model scale and agent design: LocAgent’s results use larger models and a tool that returns compressed subgraphs with relation-aware summaries, whereas our
T
arm hands a 4–8B model raw edge lines truncated at 50 and leaves the chaining to it. Scale alone does not close the gap in our harness: at none of six sizes from 0.6B to 32B is the graph arm’s depth slope flatter than the
grep
arm’s (Section 5.4), and the larger models simply call the graph tools less.
ForceTool
rules out “the agent does not call the tool” as the explanation, and
Budget
rules out budget. What is left is the model’s ability to
use
a neighbourhood listing to decide what to expand next, which is a reasoning step that, by the probe results, has no linear support in the model’s representation of the code. We think this is the right reading, but it is an inference, and a direct test—presenting multi-hop paths explicitly, or training the agent to chain expansions—is future work.
What the probes do and do not show.
Our protocol is deliberately conservative. The within-anchor, degree-binned AUC removes every node-level shortcut we could name, and the lexical baseline calibrates what “decodable” means against a trivial alternative. A linear probe is also a lower bound: a nonlinear readout, an attention-pattern analysis, or a causal intervention could find two-hop structure a linear probe cannot. The claim we make is correspondingly narrow:
linearly
, at the
definition’s last token
, the repository’s call graph beyond one hop is not represented in these models, and the one-hop part that is represented is not more than lexical. The agreement between the static probe and the in-conversation probe, including on edges the tools never printed, adds confidence that this is a property of the model and not of the context format. We also want to be explicit about the negative finding behind the design: the global pair-probe AUC of 0.75–0.80 that we obtained first, and that a less careful study would have reported, is matched by one-sided probes and by a degree baseline. We recommend the within-anchor protocol, with a stratification on the confound that matters for the relation (here, in-degree), for any relational probe.
Implications for tool design.
Three practical suggestions follow. (i) For small models, exact-name resolution is the single most valuable thing a structured tool provides, both for discovery at hop 0 and for the
form
of the submission; it is cheap and should be present even when a full graph is not. (ii) Since agents expand once and stop, a tool that returns the
two-hop
closure in a compact, ranked form, or that proposes the next expansion, is more likely to help at hop 2+ than a tool that returns raw one-hop edges. (iii) Embedding search and graph tools reveal the gold through different routes and combine additively for the 8B model and only marginally for Gemma; for Qwen3-4B-Instruct-2507 the embedding tool is dead weight and
ET
is slightly worse than
T
, while for the hybrid Qwen3-4B checkpoint of the same size it is worth
+17.6
points. Tool sets should be validated per checkpoint rather than inherited from a larger model or from another checkpoint of the same size. (iv) Beyond about 8B, a strict scorer credits the tools for the form of the submission as much as for discovery; a localization stage that canonicalises names (line numbers, :: paths, short names) recovers about half of the tools’ measured gain without any tool.
Implications for benchmarks.
Hop depth is a cheap, released, validated axis along which to report results. Aggregate function Acc@10 on SWE-bench Verified mixes 37% of tasks where the answer is named in the issue with 15% where it is three or more edges away; a method that improves the former and not the latter will look good on the aggregate and has not addressed structure. We suggest reporting the hop-3+ bucket separately, and we note that the strict-mention variant, though it discards too many tasks to be the default, is a useful conservative check on any claim about deep tasks.
Limitations.
The primary models are small (4–8B) and the mechanism experiments (Traces, Budget, ForceTool, Repair , the probes) are on the 4–8B models only. The scale curve covers 0.6B–32B with five decodings per size, but its largest model is the non-thinking Qwen3-32B served from an FP8 checkpoint, which is not stronger than Qwen3-14B at this task; the curve should not be read as an asymptote, and whether a model that calls the tools
and
is strong at
grep
would show a different curve is open. The Gemma family contributes two usable sizes (E2B, E4B); the 12B run was partial and degenerate. Canonical rescoring is available for the Qwen sizes only, and the scale curve’s 4B model is a different checkpoint from the primary 4B runs, which we treat as a finding about checkpoints rather than a confound, but which means the curve has no point for the Instruct checkpoint at 4B. The evaluation subset is 160 tasks, which limits the resolution of arm-versus-arm comparisons among the structured tools to about
\pm 5
points even with three runs; Django supplies half of the subset. The hop label is optimistic (name-based resolution, static only) and sensitive to mention extraction; depth is a shortest path, not an agent’s path. The label and the
T
arm’s tools are built from the same graph, so the hop-0/hop-1 advantage of
T
is in part an advantage
on the label’s own terms
: a target the label calls “one edge away” is one that
graph_neighbors
can print, and a resolution rule that drops an ambiguous call drops it for both. The
E
and
G
arms do not share this coupling, which makes the
E
results the cleaner test of the depth axis. The localization-only formulation removes the interaction between exploration and editing that a full agent has, and the
Repair
model is itself weak, so
Repair
bounds rather than measures the value of localization. The probes use one representation (last-token residual stream) and one family of readouts (linear); the in-conversation probe has wide intervals and is on the 4B model only. The embedding arm uses one strong and one weak embedder, not a sweep. Finally, the study was conducted on one benchmark in one language; Python’s dynamic dispatch is invisible to our graph, which both understates true depth and overstates what a static graph tool could ever return.
8
Conclusion
We labelled SWE-bench Verified with a deterministic code-graph hop depth, showed that each hop roughly halves the odds of correct function-level localization for four models from 4B to 32B after controls and at every one of six sizes from 0.6B to 32B, and released the labels. We ablated the tool set of a localization agent and found that structured tools roughly double
grep
-only accuracy for Qwen3-8B and Gemma 4 E4B, that only graph tools help Qwen3-4B, that over a scale curve from 0.6B to 32B the tools’ gain peaks at 17–21 points at 1.7–4B and falls to 4–5 at 32B as the model stops calling them (with about half of the gain from 8B up being the form of the submission), that the same size gains or does not gain from a tool depending on the checkpoint, and that the graph tools’ benefit is exact-name lookup at hop 0 and one expansion at hop 1—they do not flatten the depth gradient, and forcing their use, enlarging the budget or sampling does not change that. A fixed repair model turns those localizations into 6–13 resolved tasks of 160 against 26 with oracle locations, almost all of them on correctly localized tasks. Linear probes, once stratified to remove node-level confounds, find a direct-call representation in the middle layers that transfers across repositories and survives inside agent conversations, but that is weaker than a substring test and does not extend to two hops or to inheritance. The multi-hop structure that the deepest third of the benchmark requires is neither in these models’ weights nor, in practice, extracted from the tools we gave them. Closing that gap—by tools that return and rank multi-hop closures, by training agents to chain expansions, or by models that represent more than one hop—is the open problem this study isolates.

Gemma 4 12B.
The serving session ended during the greedy run after 307 tasks (1,228 episodes; 120/82/45/45/15 tasks at hop 0/1/2/3+/no-mention, all four arms for each). Unlike every other model in the sweep the 12B agent loops on
read_file
(15.5–16.9 calls per episode, 18–20k tokens), hits the 30-step cap in 51–57% of episodes and submits in 39–45%, so every arm scores 17–19% (strict) with the gold on screen in 88% of episodes and a conversion rate of 20–22%. Whether this is a property of the checkpoint, of the gemma4 tool-call parser in vLLM 0.32.0, or of the session is not something the partial run can settle; we report it and draw no conclusion from it.

Three models were run both in the primary experiments (Section 5.3 ; vLLM 0.19.1) and in
