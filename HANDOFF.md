## 4. Hard facts extracted from the harness README (critical for the plan)

**Evaluation**
- Score = fraction of tasks whose patch makes the hidden tests pass (pytest exit 0 + JUnit XML all required tests passed, none skipped).
- Hidden test set: ~120 tasks from **PRIVATE Python repos**, split evenly public/private LB. Curated so a frontier model passes or is within one test of passing. → Do NOT overfit to fastapi/rich knowledge; train general behavior.
- **12 hours wall-clock for ALL tasks** (inclusive of sandbox setup, exclusive of grading). ~120 tasks → ~6 min/task average if serial; scorer concurrency unknown (assume serial; design for ≤5-6 min/task or set per-task `max_time_minutes` in `eval_config.yaml`).
- Default budgets: 60 min/task, 100 tool calls, 500 turns; sample submission uses 1 min / 10 calls / 50 turns. We override via `eval_config.yaml` (`evaluation: {timeout_seconds, max_tool_calls, max_time_minutes, max_turns}`).
- Patches touching test files (`test_*.py`, `*_test.py`, `tests/`, `conftest.py`, `pytest.ini`, `pyproject.toml`, `setup.cfg`, etc.) are STRIPPED before grading. Untracked files in `/workspace` ARE included in the patch (scratch files must go in `/tmp`). If `submit_patch` is never called, harness still extracts `git diff` as fallback.
- Continuation nudges: up to 3 consecutive text-only turns without a tool call get a "please continue" message; then session ends.

**Model / serving**
- Allowed base models (exactly one per submission): `gemma-4-31b-it-qat-w4a16-ct`, `gemma-4-12b-it-qat-w4a16-ct`, `gemma-4-e4b-it-qat-w4a16-ct`, `gemma-4-e2b-it-qat-w4a16-ct`. All agents/sub-agents share the base model but **may each use a different LoRA**.
- vLLM, tensor_parallel=4 on 4x L4 (96 GB), `max_model_len=32768`, `tool_call_parser=gemma4`, `reasoning_parser=gemma4` (thinking delimited by `<|channel>` ... `<channel|>`), `enable_auto_tool_choice`. 12B needs `--hf-overrides` architectures Gemma4ForCausalLM (quirk).
- LoRA: PEFT dirs `adapters/<name>/{adapter_config.json, adapter_model.safetensors}`, `max_lora_rank` ≤128, total unpacked submission < 3 GiB. Size table: 31B r=16 ≈110-220 MB, r=64 ≈450-900 MB.
- **Open question for the plan:** adapter trained on bf16 weights vs served on QAT int4 weights → mismatch. Likely best practice: dequantize the w4a16 compressed-tensors checkpoint to bf16 (so training sees exactly the deployed weights) and train LoRA on top; or QLoRA directly. Needs verification in research phase.
- Generation config: `thinking_config.thinking_budget` 0..32768 (default 4096), `max_output_tokens` default 16384. With vLLM+LoRA, use `include_thoughts: true` + `thinking_budget`, NOT `thinking_level`.

**Context management**
- ADK EventsCompaction: interval 15 events, token_threshold 14,336, retain last 5 events, overlap 2. Context caching min 2048 tokens. → the model must cope with compacted history; a sub-agent (`agent_tool`, `skip_summarization: true`) can isolate exploration context from the coder.
- `read_file` capped at 150 lines / 10k chars; `run_command` output capped at 5000 chars, 300 s timeout; graph tool outputs capped at 5000 chars.

**Tools (9, fixed)**: run_command, submit_patch (free), get_status (free), read_file, edit_file (3-tier matching: exact → whitespace-flexible → regex), write_file, get_code_neighbors(node, edge_type, max_neighbors), search_similar_code(query, k) (resolves query against node names, cosine over precomputed 256-d embeddings; lexical fallback), get_code_subgraph(nodes). Code graphs are NetworkX multidigraphs (node = module/class/function with full source `text`; edges typed e.g. `calls`).

**Agent config**: Google ADK YAML (`agent.yaml` root), LlmAgent/SequentialAgent/ParallelAgent/LoopAgent, `!include` prompts, `sub_agents`, `agent_tool`, `skills/` dirs with SKILL.md + sandboxed python scripts (`run_skill_script`), `{problem_description}` templating. ## 7. Early strategic hypotheses (to validate in research, then turn into the plan)

1. **Scale strategy**: E4B as research vehicle (many ablations), recipe transfer to 31B for final main submission; 12B fallback.
2. **Data**: teacher budget is tiny → core engine is **execution-verified self-generated trajectories** (Gemma itself runs the agent loop on training tasks + synthetic tasks, keep trajectories whose patch passes tests; iterate = expert iteration / RFT). Synthetic tasks can be generated **without a teacher** by bug injection / reverting real commits in public repos (SWE-smith/SWE-Synth style), run inside the subprocess sandbox on Kaggle.
3. **Private-repo test set** → train for generalizable *process* (localize → read → minimal edit → run targeted tests → submit), not repo knowledge. Hold out one repo (e.g., rich) as a proxy for unseen repos.
4. **Architecture**: multi-agent YAML tree with specialist LoRAs (e.g., graph-aware localizer sub-agent as `agent_tool` to keep the coder's context clean; coder LoRA; optional verifier/critic) — exploits the harness's multi-LoRA feature and the graph tools, which few competitors will train for. Novelty angle: *training the model to use the code graph tools* (graph-tool-aware trajectories) and measuring the gain.
5. **Inference budget**: ~6 min/task → thinking budget must be small (≤2-4k), tool-call count maybe 30-50, incremental edits, scratch in /tmp, always `submit_patch`.
6. **Serving fidelity**: train LoRA on exactly the deployed quantized weights (dequantized QAT ct → bf16) to avoid train/serve mismatch; validate locally with vLLM + LoRA before submitting.
7. **Paper**: contributions could be (a) teacher-free execution-verified self-improvement for small SWE agents on consumer-class GPUs, (b) graph-tool-grounded localization training, (c) recipe scale-transfer E4B→31B, (d) ablations on multi-LoRA specialist decomposition.
